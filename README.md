# Бронь Сервис — CRM заявок

Рабочий адрес: https://bronservis51-bot.github.io/bron-crm/

Стабильная отдельная копия раздела «Заявки» основного кабинета. Канбан, ручные
контакты, карточка, ответы анкеты, поиск, заметки, перемещение, корзина и восстановление.
Вход — тем же личным логином и паролем. Права проверяются существующим сервером.
На новом адресе вход выполняется заново; сохранённая сессия из основного кабинета
не переносится. Выход из одной сессии не завершает другую. Смена пароля общая.

## Получение заявок

Лендинг → существующий `lead_submit` → общая БД.
Основной кабинет и эта CRM независимо обращаются к ней. Запись имеет один UUID;
двойная отправка, перенос данных и отдельная синхронизация не нужны. Изменения
видны в обоих клиентах после обновления списка (автоматически раз в минуту,
при возвращении в окно или по кнопке). Контроль `updated_at` защищает от старой правки.

## Выпуск

Исходник раздела: `bronservis51-bot/bron-franchise@6bfdf52` (10.11.2026).
Нет runtime-импорта кода из основного репозитория. Независимый workflow `Stable CRM`
проверяет типы, тесты и сборку перед Pages. Доработки кабинета не обновляют эту CRM.
Backend остаётся общим: несовместимые изменения RPC/Auth нужно согласовать с CRM.

`npm ci`, скопировать `.env.example` в `.env.local`, `npm run dev`.
`.env.example` содержит только публичные URL и publishable key, не секреты.
Проверки: `npm run typecheck`, `npm test`, `npm run build`.
Изменения в `main` публикуются только в эту CRM. Откат — revert проблемного commit
и успешная повторная публикация; не откатывать и не очищать общую базу.

## Связь и ограничения

Обе CRM пока используют Supabase `vkkqffvmztpzgygzfxhq` в `us-west-2`.
Работа VPN указывает на различие сетевого доступа, но не определяет точную причину.
Отдельный клиент не исправляет блокировку/маршрут к общему Auth/БД. Диагностика:
`help.html`; проверка с другой сети не подтверждает доступность у директора.
При пропаже сети открытая карточка остаётся; успешное сохранение показывает сервер.
PWA кеширует только оболочку, не заявки. Неподтверждённую запись не создавать заново.
Перенос/шлюз — отдельная задача с проверкой на реальной сети, без reset/seed.
